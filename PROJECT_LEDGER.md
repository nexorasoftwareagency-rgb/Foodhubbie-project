- Gap: `deductInventoryStock()` deducted at web/app finalization and nothing ever put it back. A cancelled or refunded browser order left the shelf short for food that was never sold, and Admin's Inventory tab showed the wrong count until someone fixed it by hand.
- Fix (`bot/index.js` only, no client, rules or Admin change):
  * `deductInventoryStock(sock, items, outlet)` now returns `{ [invId]: qtyActuallyTaken }`, clamped by what the shelf held (`Math.max(0, before - newStock)`), and records nothing for an id it did not touch. It also aggregates quantities per inventory id BEFORE writing: two lines of the same dish used to each compute `stock - qty` from the same snapshot, so the second write overwrote the first and only one line was ever deducted (a real, pre-existing stock-leak bug found while wiring this).
  * Low-stock alert: only sends when a socket exists AND a notifyPhone is configured; the old code would have thrown on `sock.sendMessage` with a null socket.
  * Finalization: `const inventoryDeducted = await deductInventoryStock(...)` and ONE `updateData(orders/{id}, { stockDeducted: true, inventoryDeducted })`. Awaiting means a cancel cannot race the deduction; writing both in one update means the map and the marker can never disagree. `stockDeducted` stays the finalization marker even when the deduct failed (`{}`) — clearing it would let the order be finalized twice (discount re-check, reward burn).
  * `restoreOrderInventory(orderId, order)` runs from the `child_changed` listener immediately after `releaseOrderDiscountUsage`, i.e. BEFORE the same-status debounce gate. Guards: `stockDeducted === true`, `stockRestored !== true`, status cancelled/refunded, not dine-in (`isDineInOrder`), and a non-empty `inventoryDeducted` map. Claims `orders/{id}/stockRestored` in a transaction (cold-tx seeded) BEFORE touching stock, then per id a cold-tx-seeded `stock + n` restore; an inventory item deleted since is skipped (returning `undefined` aborts, never resurrects a node).
- Why a recorded map instead of recomputing from `items`: a line for 5 when only 1 was on the shelf only ever took 1, so a name-based restore would invent 4 units. Orders finalized before this shipped carry no map and are skipped by design.
- Scope: only bot-finalized web/app orders. Dine-in/QR keeps session-owned stock (the guard is defensive — APP orders are pickup/delivery). Table/POS flows never used this path.
